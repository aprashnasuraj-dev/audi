# Minly VDP Research Roadmap

This roadmap optimizes for valid, unique, impact-backed findings while staying inside the VDP's low-impact testing rules. It also tracks **latent security risk**: weaknesses and assumptions that are not reportable today but could become exploitable as the product evolves.

## Phase 0 — Setup and scope freeze

Before testing:

- verify the current Minly VDP scope and save the check date;
- use the existing researcher-controlled account for normal-use mapping;
- create a second ordinary researcher-controlled account only when a two-account authorization test is needed and the product permits it;
- record account roles and ownership privately;
- use a dedicated browser/device profile;
- configure proxy/history storage so secrets can be redacted and raw captures remain private;
- keep this public GitHub repository free of live finding details.

Exit criteria: exact scope is confirmed and at least one researcher-controlled account is ready.

## Phase 1A — Public-surface mapping

Use the policy-gated GitHub workflow or a normal browser to map only the exact `https://minly.com/` public surface.

The automated mapper is intentionally limited to:

- exact host `minly.com`;
- GET-only requests;
- maximum 12 pages per run;
- at least 2.5 seconds between requests;
- no query-space expansion;
- no cross-host redirect following;
- no form submission or state mutation.

Public mapping is contextual evidence, not a finding generator.

## Phase 1B — Own-account normal-use mapping

Use the website/apps normally. Do not enumerate hidden endpoints.

Map only features naturally observed through the researcher's account:

- authentication and account recovery;
- profile/account settings;
- creator/content interactions;
- order/booking/payment-related flows if exposed;
- messaging, media, uploads, or user-generated content if present;
- API calls generated by those features;
- WebSocket events generated by normal use;
- mobile deep links/app links observed during ordinary use.

Record **security boundaries and invariants**, not just endpoints.

Exit criteria: a concise list of actors, owned objects, state-changing actions, server-controlled fields, asynchronous actions, callbacks/deep links, and role boundaries.

## Phase 1C — Adaptive risk modeling

Run the mapped workflows through `AI_REVIEW_PROTOCOL.md` and `adaptive-audit-profile.yml`.

Every candidate is classified as one of:

1. **confirmed exploitable** — manually reproduced, impact demonstrated;
2. **security weakness** — concrete weakness, abuse path not yet proven;
3. **latent vulnerability** — current safety depends on a fragile assumption/control;
4. **attack-path precursor** — material mainly when chained with another condition;
5. **security enhancement** — defensive improvement without demonstrated exploitability.

Only class 1 is directly submission-eligible. Classes 2–5 are research/prioritization inputs.

For each workflow, challenge:

- ownership checks;
- role/entitlement transitions;
- session/recovery state;
- client-controlled vs server-controlled fields;
- stale authorization in background jobs;
- cache/CDN personalization boundaries;
- callback/deep-link trust;
- web/mobile authorization parity;
- feature-flag or UI-hidden capability assumptions;
- upload/media serving boundaries.

## Phase 2 — Authorization-first testing

Highest-value sequence:

1. create an object/action in Account A;
2. capture the normal request generated by the product;
3. create Account B only if a cross-account proof is required;
4. replay the minimum equivalent operation from Account B;
5. change only the ownership/object identifier necessary for the hypothesis;
6. stop as soon as the server either rejects correctly or demonstrates unauthorized access.

Do not guess unrelated IDs or enumerate users.

Priority hypotheses:

- read another controlled account's object;
- edit/delete another controlled account's object;
- perform a state change across roles;
- call a backend action hidden by the UI but observed through normal use;
- bypass ownership enforcement after switching accounts;
- retain entitlement after revocation/downgrade;
- execute an asynchronous action after authorization state changed.

## Phase 3 — Authentication and recovery

Test only researcher-controlled accounts:

- login/session transitions;
- account switching;
- recovery links/codes;
- email/phone ownership checks;
- stale/replayed recovery artifacts where a minimal proof is possible;
- sensitive actions immediately after credential/session transitions;
- whether revoked/rotated sessions remain effective across web/mobile clients.

Stop before any action that would target a real third-party identifier.

## Phase 4 — Business logic and state machines

Focus on invariants, not volume:

- one-time actions repeated once where safe;
- order/booking ownership;
- entitlement transitions;
- price/quantity/coupon/refund logic using reversible or non-monetary proof;
- impossible state transitions;
- client-controlled fields that should be server-controlled;
- delayed/background processing after state or authorization changes;
- retry/idempotency behavior where one reversible replay is sufficient.

Do not cause financial loss, duplicate fulfillment, spam, or service disruption.

## Phase 5 — Input, callbacks, and client boundaries

Website:

- stored/reflected input handling only where impact is meaningful;
- upload behavior using harmless files;
- URL/redirect/callback handling using benign researcher-controlled destinations;
- server-side fetch behavior only with safe public destinations controlled by the researcher;
- cache/personalization behavior using only anonymous and researcher-owned sessions.

Mobile:

- app/deep links;
- exported component behavior with direct Minly impact;
- WebView/native bridge boundaries;
- app-to-backend authorization;
- web/mobile parity for the same operation;
- non-rooted local/inter-app exposure.

## Phase 6 — Offline artifact analysis

If a legitimate app/source/capture artifact is available, use the advanced toolchain **offline**:

- Semgrep for static patterns;
- Bandit for Python artifacts;
- Trivy for filesystem/SBOM/IaC context;
- pip-audit for Python dependency context;
- JADX/apktool/aapt/apksigner for Android package structure;
- mitmproxy only for researcher-controlled traffic capture/review.

Static/tool findings remain hypotheses until manually tied to a real Minly impact.

## Phase 7 — Candidate triage

For every candidate:

1. run `FINDING_ELIGIBILITY_GATE.md`;
2. classify it using the adaptive risk classes;
3. score with `SUBMISSION_SCORECARD.md`;
4. reproduce in a clean session;
5. reduce the PoC to the minimum number of steps/requests;
6. redact evidence;
7. draft with `SUBMISSION_TEMPLATE.md`.

A speculative future risk must never be submitted as a present vulnerability.

## Phase 8 — Submit and retest

- submit through `https://vdp.minly.com/`;
- record portal reference privately;
- preserve confidentiality;
- answer triage questions with the same minimal evidence standard;
- retest only after Minly requests or reports a fix;
- do not publicly disclose until Minly permits it.

## Time allocation

Recommended effort weighting:

- 30% authorization/ownership boundaries;
- 20% authentication/recovery/session state;
- 20% business logic/state machines;
- 10% async/cache/feature-flag latent-risk review;
- 10% API consistency discovered through normal product use;
- 5% mobile-specific deep-link/WebView/backend-parity review;
- 5% input handling with demonstrated impact.

Avoid spending time on categories the program explicitly excludes unless they form one step in a larger, demonstrated exploit chain.
