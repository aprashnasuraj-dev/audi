# Minly VDP Research Roadmap

This roadmap optimizes for valid, unique, impact-backed findings while staying inside the VDP's low-impact testing rules.

## Phase 0 — Setup and scope freeze

Before testing:

- create two researcher-controlled Minly accounts where the product permits it;
- record account roles and ownership in a private worklog;
- verify the live VDP scope and save the check date;
- use a dedicated browser profile/device profile;
- configure proxy/history storage so secrets can be redacted and raw captures remain private;
- keep this public GitHub repository free of live finding details.

Exit criteria: exact scope is confirmed and test accounts are ready.

## Phase 1 — Normal-use mapping

Use the website and apps normally. Do not enumerate hidden endpoints.

Map only features you naturally observe:

- authentication and account recovery;
- profile/account settings;
- creator/content interactions;
- order/booking/payment-related flows if exposed to your account;
- messaging, media, uploads, or user-generated content if present;
- API calls generated by those features;
- mobile deep links/app links observed during ordinary use.

Record security boundaries, not just endpoints.

Exit criteria: a concise list of owned objects, state-changing actions, and role boundaries.

## Phase 2 — Authorization-first testing

Highest-value sequence:

1. create an object/action in Account A;
2. capture the normal request generated by the product;
3. replay the minimum equivalent operation from Account B;
4. change only the ownership/object identifier necessary for the hypothesis;
5. stop as soon as the server either rejects correctly or demonstrates unauthorized access.

Do not guess unrelated IDs or enumerate users.

Priority hypotheses:

- read another controlled account's object;
- edit/delete another controlled account's object;
- perform a state change across roles;
- call a backend action hidden by the UI;
- bypass ownership enforcement after switching accounts.

## Phase 3 — Authentication and recovery

Test only your own accounts:

- login/session transitions;
- account switching;
- recovery links/codes;
- email/phone ownership checks;
- stale/replayed recovery artifacts where a minimal proof is possible;
- sensitive actions immediately after credential/session transitions.

Stop before any action that would target a real third-party identifier.

## Phase 4 — Business logic

Focus on invariants, not volume:

- one-time actions repeated once where safe;
- order/booking ownership;
- entitlement transitions;
- price/quantity/coupon/refund logic using reversible or non-monetary proof;
- impossible state transitions;
- client-controlled fields that should be server-controlled.

Do not cause financial loss, duplicate fulfillment, spam, or service disruption.

## Phase 5 — Input and client boundaries

Website:

- stored/reflected input handling only where impact is meaningful;
- upload behavior using harmless files;
- URL/redirect/callback handling using benign researcher-controlled destinations;
- server-side fetch behavior only with safe public destinations you control.

Mobile:

- app/deep links;
- exported component behavior with direct Minly impact;
- WebView/native bridge boundaries;
- app-to-backend authorization;
- non-rooted local/inter-app exposure.

## Phase 6 — Candidate triage

For every candidate:

1. run `FINDING_ELIGIBILITY_GATE.md`;
2. score with `SUBMISSION_SCORECARD.md`;
3. reproduce in a clean session;
4. reduce the PoC to the minimum number of steps/requests;
5. redact evidence;
6. draft with `SUBMISSION_TEMPLATE.md`.

## Phase 7 — Submit and retest

- submit through `https://vdp.minly.com/`;
- record portal reference privately;
- preserve confidentiality;
- answer triage questions with the same minimal evidence standard;
- retest only after Minly requests or reports a fix;
- do not publicly disclose until Minly permits it.

## Time allocation

Recommended effort weighting:

- 35% authorization/ownership boundaries;
- 20% authentication/recovery;
- 20% business logic;
- 10% API consistency discovered through normal product use;
- 10% mobile-specific app/deep-link/WebView boundaries;
- 5% input handling with demonstrated impact.

Avoid spending time on categories the program explicitly excludes unless they form one step in a larger, demonstrated exploit chain.
