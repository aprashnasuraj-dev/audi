# Minly Advanced Audit Plan

This plan extends the Minly VDP blueprint into a deeper, researcher-controlled audit track without broad scanning or testing outside the published program scope.

## Operating model

The audit has three layers:

1. **Public-surface mapping** — low-volume browser discovery of `https://minly.com/` only.
2. **Authenticated own-account mapping** — the researcher logs in locally and exports Playwright storage state; GitHub Actions consumes that state without receiving the password.
3. **Manual authorization verification** — candidate object references and state-changing requests are ranked for human A/B testing using only researcher-controlled accounts. Automated cross-account exploitation is intentionally not performed.

## Exact scope boundary

### Allowed

- `https://minly.com/` and paths on the exact host `minly.com`.
- The official Minly iOS application (App Store ID `1528802350`).
- The official Minly Android application (package `com.minly.users`).
- Requests generated by normal use of those in-scope applications, provided the destination being tested is itself in scope.

### Observe but do not test

- Third-party static resources needed to render the website.
- External payment, analytics, CDN, support, identity, or social-login services.
- Apple App Store and Google Play infrastructure.

### Explicitly do not expand to

- Any Minly subdomain that is not explicitly listed by the program.
- `merch.minly.com` or any other discovered sibling host unless Minly updates the VDP to include it.
- Any third-party service merely linked, embedded, redirected to, or called by an in-scope client.

The workflow therefore authorizes only the exact host `minly.com` and treats every subdomain as denied for active audit traffic.

## Service surface to map

Public site research indicates the following product areas are worth mapping with normal user interaction:

- creator/profile browsing;
- personalized shoutout/video request flows;
- private direct-message interactions;
- shared video pages under `/v/<opaque-token>`;
- online/live/on-demand event access;
- business/brand booking flows;
- creator/talent enrollment;
- account/profile/session workflows;
- purchase, order, booking, entitlement, refund/cancellation, and delivery state transitions that appear during normal own-account use.

This is a research map, not an assumption that every feature is present in the current account or region.

## Highest-value hypotheses

### Authorization and object binding

Prioritize requests containing order IDs, booking IDs, conversation/message IDs, media IDs, event entitlement IDs, profile IDs, recipient IDs, or opaque share tokens. Candidate generation is offline only. Verification must use resources created by Account A and Account B, both controlled by the researcher.

Questions to answer manually:

- Can Account B read, update, cancel, download, or otherwise act on an object created by Account A?
- Can a public/share token reveal more information than intended?
- Does changing the client-side object identifier alter server-side authorization?
- Are state-changing endpoints authorization-checked independently of UI visibility?
- Are media/download endpoints bound to the purchaser/recipient/entitlement?

### Workflow integrity

Focus on state transitions rather than volume:

- booking/request lifecycle;
- payment-initiation versus payment-confirmed state;
- cancellation/refund eligibility;
- one-time or limited-use actions;
- event/watch entitlements;
- private-message or private-media visibility;
- creator/customer role boundaries;
- web/mobile consistency for the same object.

Never create financial loss, charge another person, interfere with creators, or manipulate third-party payment providers. Stop once a minimal proof is sufficient.

### Session/account boundaries

Use the researcher's own account only. Inspect:

- login/session renewal behavior;
- sensitive action re-authentication;
- session isolation across browser profiles;
- account email/phone/profile changes;
- old-session behavior after security-sensitive account changes.

Password-policy quality and expected stateless JWT persistence after logout remain excluded by the program unless a separate direct exploit is demonstrated.

### Mobile-specific depth

When the official app package/binary is available to the researcher, prefer offline analysis first:

- exported components / URL schemes / app links;
- WebView/native bridge boundaries;
- sensitive intent handling;
- local route and API inventory;
- hard-coded environment endpoints;
- client-enforced authorization assumptions;
- differences between mobile and web request schemas.

Do not report missing pinning, lack of obfuscation, rooted-device-only storage access, or third-party-library versions without a direct Minly exploit.

## Toolchain philosophy

The advanced workflow deliberately avoids mass scanners, subdomain enumeration, brute force, directory fuzzing, denial-of-service tests, or automated exploit chains. It uses:

- Playwright/Chromium for normal browser navigation;
- HALO exact-scope discovery and low-rate evidence collection;
- HAR sanitization and endpoint inventory;
- offline parameter/object-reference candidate extraction;
- offline JWT metadata inspection for researcher-owned tokens;
- Semgrep against locally captured first-party JavaScript only when such files are supplied;
- optional JADX/apktool/MobSF-style offline mobile analysis when the researcher supplies the official app package;
- human verification gates before any submission.

## Session workaround

The repository never needs the Minly password. Run the local session capture helper, authenticate manually in Chromium, and export Playwright storage state to a local ignored file. Encode that file as a GitHub Actions secret named `MINLY_STORAGE_STATE_B64` if an authenticated runner audit is desired.

Storage state, HAR files, tokens, screenshots containing personal data, and private findings must never be committed to this public repository.
