# Website Test Matrix

Target: `https://minly.com/`

This matrix is manual-first and intentionally avoids high-volume scanning. Use two researcher-controlled accounts where a cross-account boundary must be tested. Stop immediately if unrelated user data appears.

## Priority 1 — Authentication and account boundaries

| Area | Safe test idea | Evidence of a valid issue | Stop condition |
|---|---|---|---|
| Login/session | Compare logged-out vs logged-in behavior using your own account | Protected action/data remains accessible without the required session | Any unrelated account data appears |
| Account recovery | Exercise recovery only for your own account(s) | Recovery can be completed without the intended ownership proof | Flow would target another person's email/phone |
| Object authorization | Create resource in Account A; attempt the same operation from Account B using only researcher-owned accounts | Account B can read/change/delete Account A resource without authorization | Any ID belongs to a third party |
| Role/privilege boundary | Use only roles legitimately available to your own accounts | Lower-privilege account performs an action reserved for higher privilege | Elevated privilege cannot be safely obtained with own account |

## Priority 2 — Sensitive state changes and business logic

| Area | Safe test idea | Evidence of a valid issue | Notes |
|---|---|---|---|
| Profile/settings | Modify only your own profile and second test account | Cross-account or unauthenticated state change | Avoid low-impact login/logout CSRF-only reports |
| Orders/bookings/purchases | Use reversible/non-monetary steps wherever possible | Price, quantity, entitlement, or ownership invariant can be bypassed | Do not cause financial loss or irreversible fulfillment |
| Coupons/credits/refunds | Test with researcher-owned transactions only | Repeat/replay/manipulation creates unauthorized value | Stop once impact is demonstrated |
| Workflow state | Change request parameters across valid state transitions | Server accepts an impossible/unauthorized state transition | Keep request count minimal |

## Priority 3 — Input handling with demonstrated impact

| Area | Safe test idea | Valid evidence |
|---|---|---|
| Stored/reflected HTML/JS injection | Test only fields visible to your own account/session first | Script execution in a security-relevant Minly origin/context with meaningful impact |
| URL/redirect handling | Use benign destinations you control | Redirect or callback behavior creates credential/session/security impact, not just cosmetic navigation |
| File upload | Upload harmless files to your own content area | Server-side execution, unauthorized read/write, or meaningful content-type enforcement failure |
| Server-side fetch features | Use a benign endpoint you control and non-sensitive destinations | Demonstrable server-side request behavior without probing internal/private ranges |

## Priority 4 — API behavior discovered through normal use

Capture API requests generated by the browser while using your own account. Prefer replaying a single observed request over endpoint enumeration.

Check:

- authorization consistency across your two controlled accounts;
- server-side enforcement of ownership identifiers;
- method/parameter changes that remain within the same observed feature;
- excessive data returned for your own objects;
- mutation replay/idempotency only where it cannot create harmful duplicates;
- predictable identifiers only when tested against your own records.

Do **not** enumerate other users, guess IDs at scale, or scrape data.

## Explicitly low-value/out-of-scope for this program

Do not spend reporting effort on these unless they directly enable a separate demonstrated exploit:

- missing HSTS/CSP/other headers;
- weak TLS configuration alone;
- software/version disclosure;
- stack traces without exploitability;
- clickjacking without a sensitive action;
- self-XSS;
- login/logout CSRF;
- password complexity/expiry policy;
- SPF/DKIM/DMARC;
- non-critical endpoint rate limiting.

## Per-session limits

- Begin with normal browser behavior and one request at a time.
- Use the smallest number of requests necessary to validate a hypothesis.
- Do not run broad crawlers, brute-force wordlists, fuzz storms, or concurrency/load tests.
- Stop after a minimal proof demonstrates the issue.
