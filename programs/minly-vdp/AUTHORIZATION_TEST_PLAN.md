# Authorization-First Manual Test Plan

This plan is limited to Minly's explicitly in-scope assets and two researcher-controlled ordinary accounts: Account A and Account B.

The purpose is to detect horizontal authorization failures without touching any unrelated user's data.

## Core method

For each user-owned object class that actually exists:

1. Create or identify one object owned by Account A.
2. Create or identify the equivalent object owned by Account B.
3. Confirm each owner can access its own object normally through the product UI.
4. Record the normal request shape for A and B using a browser/mobile proxy or developer tools, keeping traffic manual and low volume.
5. Perform a single controlled cross-account comparison using only the A-owned and B-owned identifiers.
6. Test read access first.
7. Test write/update/delete only when reversible, harmless, and necessary to prove impact.
8. Stop immediately if any non-public data belonging to an uncontrolled user is exposed.

Do not enumerate identifiers, fuzz large ranges, scrape object IDs, brute force tokens, or automate high-volume requests.

## Expected authorization invariant

For every private object `O` owned by Account A:

- Account A may access `O` according to normal product rules.
- Account B must not receive Account A's private representation of `O` merely by presenting or modifying an object reference.
- Account B must not modify, cancel, delete, download, or otherwise act on `O` unless the normal product explicitly grants such access.

The same must hold with A and B reversed.

## Test cases

### A01 — Profile read isolation

Precondition: Account A and Account B each have a normal user profile.

Check:

- observe Account A's own profile request;
- observe Account B's own profile request;
- compare whether any user/account identifier controls the resource;
- use only the two controlled identifiers for one cross-account read comparison.

Pass condition: B cannot obtain private A profile fields beyond what is intentionally public, and vice versa.

### A02 — Profile update isolation

Only if the profile update request exposes an account/object reference.

Use a harmless field such as a synthetic display/test marker. Never change email, phone, password, payment, or recovery details merely to test authorization unless absolutely required for a confirmed issue.

Pass condition: B cannot update A's private profile through a substituted controlled identifier.

### A03 — Account settings isolation

Check user-owned settings exposed by the ordinary account UI.

Pass condition: each account can read/change only its own settings.

### A04 — Favorites/saved-item isolation

Only if favorites or saved items exist.

Create one harmless saved item under each account. Compare read/remove behavior using only A/B-owned objects.

Pass condition: A and B cannot manipulate each other's saved-item records.

### A05 — Content request ownership

Only if a draft or harmless request object can be created without causing unwanted celebrity/staff interaction or payment.

Prefer a draft/unsubmitted object. If the product immediately sends requests to a celebrity, do not create unnecessary requests merely for testing.

Pass condition: request details, status, edit, cancel, and related private data remain owner-bound.

### A06 — Order/receipt isolation

Only if a legitimate researcher-owned transaction already exists or one minimal transaction is intentionally made.

Pass condition: A cannot read B's receipt/order details or vice versa.

Do not test payment provider infrastructure directly.

### A07 — Wallet/credit isolation

Only if the feature exists.

Read-only comparison first.

Pass condition: balances, ledger details, or credit objects remain isolated. Do not attempt value manipulation as an exploratory test.

### A08 — Event entitlement isolation

Only if researcher-owned event access exists.

Pass condition: one account cannot obtain another account's private entitlement, ticket, access token, or paid stream through reference substitution.

### A09 — Purchased media isolation

Only for media legitimately belonging to Account A/B.

Pass condition: private/purchased media URLs or object references are authorization-bound, not merely obscured by an identifier.

Do not search for other users' media identifiers.

### A10 — Messages/advice threads

Only if Account A/B can create a benign thread without burdening a celebrity or unrelated user.

Pass condition: thread metadata/content remains isolated between controlled accounts.

### A11 — Notification isolation

Compare only notifications generated by normal actions on the two controlled accounts.

Pass condition: one account cannot read or acknowledge the other's private notification object.

### A12 — Support-ticket isolation

Only if a ticket can be created without unnecessary operational burden. Use a harmless test/support question and identify it as a researcher-controlled account if appropriate.

Pass condition: each account can access only its own support records unless sharing is explicitly intended.

### A13 — Account-deletion authorization

Use only a disposable research account and only when the deletion flow can be safely observed.

Pass condition: Account A cannot initiate deletion or destructive account action for Account B by changing an identifier/reference.

## Evidence standard for a candidate issue

A reportable authorization failure should have all of the following:

- both source and target accounts are researcher-controlled;
- normal own-object request/response shown first;
- exactly one or a minimal number of cross-account comparisons;
- clear unauthorized effect or private-data exposure;
- no unrelated user's data accessed;
- no high-volume enumeration;
- proof is reproducible manually;
- secrets and personal information are redacted;
- impact is described concretely, not as a theoretical best-practice concern.

## Triage decisions

### Report immediately and stop deeper testing when

- Account B receives Account A's private data;
- B can modify/delete/cancel A-owned state;
- B can obtain A's paid/private media or entitlement;
- a sensitive account action crosses the A/B boundary.

Use only enough evidence to demonstrate impact. Do not expand to other users.

### Do not report as a vulnerability when

- the object is intentionally public;
- the response contains only public profile data;
- the difference is cosmetic or cache-related;
- the test concerns an explicitly out-of-scope best practice;
- the result requires high-volume guessing/enumeration to be meaningful;
- the affected system is a third-party service outside Minly's stated scope.
