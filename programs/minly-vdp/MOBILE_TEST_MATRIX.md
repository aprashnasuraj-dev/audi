# Mobile Test Matrix

In-scope apps:

- iOS: App Store ID `1528802350`
- Android: package `com.minly.users`

Use only official store builds and researcher-controlled accounts. This plan focuses on Minly-controlled behavior, not generic OS hardening.

## Priority 1 — Authentication, sessions, and authorization

- Verify login/logout/session transitions using only your accounts.
- Compare app-visible authorization with the corresponding backend response.
- Use two researcher-controlled accounts to test ownership boundaries for profile, order, booking, message, media, or other app-created objects.
- Test token/account switching only with your own identities.
- Look for cases where the app hides an action but the backend still accepts it from an unauthorized researcher-controlled account.

A valid report needs direct Minly impact. Expected stateless JWT validity after logout alone is explicitly not enough.

## Priority 2 — Deep links, intents, universal links, and app links

Safely inspect routes reachable through documented or naturally observed links.

Check whether a link can:

- perform a sensitive action without authentication/confirmation;
- open another researcher's controlled resource without ownership checks;
- leak a Minly session/token into a destination controlled by the researcher;
- bypass a server-side workflow or permission check.

Do not report mere existence of an exported route/component without security impact.

## Priority 3 — WebViews and embedded web content

For Minly-controlled web content loaded inside the app, check:

- unsafe bridging between web content and native privileged functions;
- sensitive actions reachable from untrusted content;
- Minly credentials/session material exposed to a researcher-controlled origin;
- navigation that bypasses intended origin restrictions.

Generic WebView configuration concerns are not report-ready without a working, safe proof of impact.

## Priority 4 — Local data and inter-app exposure

Only report storage/exposure issues that are reachable on a normal, non-rooted/non-jailbroken device or via a realistic app-to-app path.

Potentially valid examples:

- Minly tokens or secrets exposed through an unintended exported component/provider;
- sensitive Minly data written to broadly accessible locations;
- backup/share/clipboard/log behavior exposing session material to another ordinary app under realistic conditions.

Do not report data that is properly protected inside app sandbox/Keychain/Keystore and requires root/jailbreak to access.

## Priority 5 — Backend/API behavior observed from the app

Prefer passive capture of requests generated by normal use, then manually replay the minimum needed request.

Check:

- object ownership enforcement using two researcher-controlled accounts;
- hidden client fields trusted by the server;
- privilege/role decisions enforced only in the UI;
- replay of state-changing calls where proof can be kept reversible;
- excessive data returned for the researcher's own records.

Do not enumerate IDs, users, creators, or orders at scale.

## Mobile-specific exclusions to enforce

Do not submit the following unless a separate direct Minly exploit is demonstrated:

- Android/iOS platform vulnerabilities;
- attacks requiring physical access to an unlocked device;
- missing certificate pinning by itself;
- vulnerable third-party library version without exploitation against Minly;
- sandboxed data accessible only after root/jailbreak;
- lack of code obfuscation;
- lack of root/jailbreak detection;
- local app crash/DoS with no backend/system impact.

## Evidence standard

A mobile submission should include:

1. exact app/platform/version tested;
2. device OS version;
3. researcher-controlled account role(s);
4. exact screen/route/API request involved;
5. minimal reproduction steps;
6. expected vs actual security decision;
7. demonstrated impact;
8. screenshots/video/request-response excerpts with all tokens and unrelated data redacted.
